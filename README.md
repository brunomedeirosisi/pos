# POS Starter (Web + API + Agent) – DBF Migration Ready

A minimal, production-lean starter for a **POS Web** with:
- **Backend**: Node.js + Express + TypeScript + `pg` (PostgreSQL)
- **Frontend**: React + TypeScript + Vite (PWA-ready)
- **Windows print agent**: outbound HTTPS worker for store installations; legacy loopback HTTP stub available for development
- **Infra**: Docker Compose (Caddy reverse proxy with internal TLS, API, Postgres, Redis)

## Instalação em loja Windows (2 caixas / 1 impressora)

O instalador tem dois modos: **Principal** (serviços Docker, banco, HTTPS e agente Windows) e **Terminal** (navegador e pareamento). As imagens prontas e o runtime estão no pacote; a loja não compila código nem executa seeds demonstrativos.

- [Guia completo de instalação e operação](docs/instalacao/USO.md)
- [Arquitetura, build, segurança, atualização e recuperação assistida](docs/instalacao/TECNICO.md)
- [Checklist de homologação física e operacional](docs/instalacao/HOMOLOGACAO.md)
- [Registro da implementação e evidências](docs/technical-audit/22-instalador-windows.md)

Para gerar o pacote no Windows com Docker Linux/amd64:

```powershell
./infra/installer/Build-Installer.ps1 -Version '1.0.0-store.1'
```

Distribua o ZIP inteiro de `artifacts/POS-Loja-<versão>.zip` por canal confiável com seu SHA256. Extraia e abra `Instalar-POS.exe` no Caixa 1. O instalador gera `Terminal-POS` para o Caixa 2. A inicialização automática ocorre após login na conta Windows da instalação. Consulte os guias para os pré-requisitos de rede, Docker, impressora e backup externo e os gates de produto ainda pendentes antes de vendas reais.

## Quickstart (desenvolvimento)

```bash
# 1) Node 24.21.0: generate unique local credentials without printing them
node infra/setup-dev-env.mjs

# 2) docker compose up (first build takes a bit)
docker compose up --build
```

Then open: `https://pos.localhost/`

> The initial certs are generated by **Caddy** with **internal TLS**. Your browser may require trusting the local CA on first run.

### Local HTTPS Without Cost

For `https://pos.localhost`, a public/free CA certificate is **not** viable because `localhost` is not a publicly validated domain.
The supported approach in this project is:

1. Start the stack:
```bash
docker compose up -d reverse-proxy
```
2. Trust the local Caddy development CA on Windows:
```powershell
powershell -ExecutionPolicy Bypass -File .\infra\install-dev-certificate.ps1
```

This installs the generated Caddy root certificate into `Cert:\CurrentUser\Root`, which removes `NET::ERR_CERT_AUTHORITY_INVALID` for `https://pos.localhost`.

To remove it later:
```powershell
powershell -ExecutionPolicy Bypass -File .\infra\remove-dev-certificate.ps1
```

### Services

- **reverse-proxy**: Caddy at `https://pos.localhost`
- **api**: Node/Express at `http://api:8080` (proxied by Caddy)
- **frontend**: unprivileged Nginx at `http://frontend:8080` (proxied by Caddy)
- **db**: PostgreSQL 16 with initial schema (`sql/init.sql`)
- **redis**: Redis 7 (required by the legacy import worker embedded in the API)
- **agent**: local peripherals stub (runs on host or separate machine; not in compose by default).

### Endpoints

- `GET /api/v1/health` – health check
- `GET /api/v1/metrics` – Prometheus metrics (`METRICS_TOKEN` is mandatory in production; send it as `x-metrics-token`)
- `GET /api/v1/products` – list products
- `POST /api/v1/products` – create product
- `GET /api/v1/products/:id` – get product
- `PATCH /api/v1/products/:id` – update product

### Generated Product and Customer Codes

- New products and customers no longer expose a manually entered legacy identifier in the creation flow.
- The API generates a unique incremental numeric code automatically from the current database state.
- For compatibility with existing imports and reports, the generated value is still persisted in `legacy_code`.

### Authentication Bootstrap

- Fresh databases no longer create a predictable default administrator account.
- To create the first administrator safely, set these three env vars together before starting the API:
  - `BOOTSTRAP_ADMIN_EMAIL`
  - `BOOTSTRAP_ADMIN_PASSWORD`
  - `BOOTSTRAP_ADMIN_FULL_NAME`
- The API will create that admin user once if the email does not exist yet.
- After the first successful start, remove those env vars from the environment or `.env`.

### Browser Authentication

- The web application now uses an `HttpOnly` session cookie instead of persisting the JWT in `localStorage`.
- Browser requests keep using `credentials: include`; the frontend no longer needs to attach `Authorization` manually.
- The backend still accepts `Bearer` tokens for non-browser clients and automated tests.
- Cookie settings are configurable through:
  - `AUTH_COOKIE_NAME`
  - `AUTH_COOKIE_MAX_AGE_SECONDS`

### Observability

- Each request now receives an `x-request-id` correlation id (reused when client sends one).
- API logs are structured (JSON via `pino`) and include request id, route template, latency, and status code.
- Prometheus metrics are exposed on `/api/v1/metrics` with default process/runtime counters plus HTTP request metrics.
- In production, set `METRICS_TOKEN` and send it through header `x-metrics-token`.

### Customer Payment & Debt Management

- Register customer payments with balance validation, view history with filters/sorting, and print receipts or full history reports from the frontend.
- API additions:
  - `GET /api/v1/customers/{id}/payments` – history + summary (supports `start_date`, `end_date`, `method`, `sort`)
  - `POST /api/v1/customers/{id}/payments` – registers payment and returns updated balances
  - `GET /api/v1/customers/{id}/payments/report` – printable history with totals/company header
  - `GET /api/v1/customers/{customerId}/payments/{paymentId}/receipt` – receipt payload with previous/new balance
- Configure company header on receipts/reports via `COMPANY_NAME`, `COMPANY_ADDRESS`, `COMPANY_TAX_ID` in your environment.

### Sales Receipt Printing

- POS checkout now collects payment method, amount paid, and change before saving the sale.
- Sale persistence no longer trusts browser-submitted item prices or totals:
  - the API recalculates each item price from the product catalog before saving;
  - `cash` prefers `product.price_cash`;
  - `card`, `bank`, `other`, `credit`, and `credit_with_entry` prefer `product.price_base` with fallback to `price_cash`;
  - subtotal, total, pending amount, and change are normalized on the server.
- Completed sales now write aggregated `stock_movement` rows per product with `type = 'venda'`.
- Cancelling a sale writes the inverse `stock_movement` entries with `type = 'entrada'`, keeping operational stock and the critical-stock dashboard consistent.
- Cancelling a sale is now blocked when it would leave a customer with credit balance from prior on-account payments, preserving receivables consistency.
- Role discount limits are enforced as percentages of the recalculated subtotal, matching the admin UI label.
- The checkout order number remains optional; leaving it blank no longer blocks the sale submission.
- Completed sales can print a receipt immediately or finish without printing.
- Reprinting is available from sales history and sale details.
- A matrix-friendly plain-text receipt endpoint is available at:
  - `GET /api/v1/sales/{id}/receipt`
  - `POST /api/v1/sales/{id}/receipt/print`
- Operational details: `docs/sales-receipts.md`
- For Docker deployments, the API expects a host print agent by default:
  - `PRINT_AGENT_URL=http://host.docker.internal:9222/print`

### Legacy Import (Phase 5)

- Queue is persistent (`Redis + BullMQ`) with retry and DLQ.
- Import status now includes stage checkpoints.
- Versioned reconciliation reports:
  - `GET /api/v1/admin/import/legacy/{sessionId}/report` (CSV)
  - `GET /api/v1/admin/import/legacy/{sessionId}/report.json` (JSON v1)
- Legacy import schema must be applied via versioned migrations (`backend/sql/migrations`), not by runtime table creation.

### Executive Dashboard KPIs

- New management dashboard API under `GET /api/v1/dashboard/*` with global filters and widget-oriented endpoints.
- Includes summary KPIs, customer KPIs, critical stock, top product, categories, sales-by-day, peak hours, seller ranking, and product ABC.
- The critical stock widget now reflects POS checkout and sale cancellation flows because those operations persist stock movements automatically.
- Implementation and formulas documented in:
  - `docs/dashboard-executive-kpis.md`

### PWA & Offline

This starter registers a basic service worker and includes a `manifest.webmanifest`. Extend `src/sw.ts` and caching strategy.

### Visual Design System

- The application now follows the Magazine Medeiros visual baseline (sidebar/topbar shell, brand palette, Inter typography, standardized UI primitives).
- Reference implementation details: `docs/design-system-visual-remodel.md`.
- Brand assets in use:
  - `frontend/public/assets/branding/logo.png`
  - `frontend/public/favicon.svg`


### Migration (DBF → Staging → Core)

- Place your **staging CSVs** in `backend/sql/staging/` and craft `backend/sql/migrate_staging.sql`.
- Use `backend/scripts/etl.ts` as the starting point for pipeline steps (CSV→staging→core).

## Notes

- This is a **starter**. You will add authentication (JWT/refresh), RBAC, more entities, tests, and robust printing/TEF integrations.
- For local printing, run the **agent** on the PDV machine:
  ```bash
  cd agent
  npm i
  npm start
  ```
  By default, Docker Compose points the API container to `http://host.docker.internal:9222/print`.

### Validation with Docker

Use Node 24.21.0 and Docker Compose (verified with 5.5.1). This command runs backend, frontend, agent, integration/regression suites, measurement controls, lint/typechecks/builds, synthetic seed checks, image smoke and backup recovery:

```powershell
node infra/test-disposable.mjs --docker --images --backups --seeds
```

Test dependencies are installed from the lockfiles inside dedicated Docker images; no local npm installation or node_modules is needed. The harness recreates only `pos-phase0-tests` and, with `--seeds`, `pos-seed-tests`. Their PostgreSQL data uses tmpfs, published ports use dynamic loopback bindings, and the harness removes their containers, networks and volumes afterward. [Test guide and scope](docs/testing-docker.md).

The original host-runner mode remains available without `--docker` and requires local test dependencies and `NPM_CLI` pointing to npm/bin/npm-cli.js. Restore and legacy overwrite remain disabled by default pending recovery validation. Applying the authentication migration invalidates previous stateless sessions; operators must sign in again.
